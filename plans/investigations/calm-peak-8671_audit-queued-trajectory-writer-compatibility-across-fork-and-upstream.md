# Queued trajectory writer compatibility audit

## Scope and provenance

- Fork batching snapshot: `47c4aff1db6711da928b37f8abec379dce8f169e` (`feat(trajectory): add batched file writer with persistent handle and debounced flushing`).
- Fork type snapshot: `7dd48ebcb8db74460a2bbd6b43ea46afd4233828` (`fix: align sync branch runtime diagnostic types`), a descendant of `47c4aff1db67`.
- Upstream comparison snapshot: `4b85d834ed1586062f31bded2f358fc5192d1674`.
- The fork and upstream snapshots diverge after merge base `538d36eaaaa6349a6539a2ad3d13dac7ed4c1f1d`; the fork commits are not changes on the upstream snapshot's ancestry.
- This is a static source/history/test audit. Per scope, no product code was changed, no tests were executed, no live state was inspected, and no external repository or Git lifecycle operation was used.
- Upstream `src/infra/fs-safe.ts` delegates regular-file append behavior to pinned `@openclaw/fs-safe` `0.5.2` (`4b85d834:package.json:2017`). The exact dependency source is not present in the named Git snapshot and external repository inspection was out of scope, so this report uses the OpenClaw call site and its existing outcome tests, not uninspected dependency internals, as proof.

## Type alignment assessment

`7dd48ebcb8db` changes no runtime branch. It adds `"file-replace"` to the shared queued-writer diagnostic union, replaces the trajectory-local widened type with a direct alias, and adds an explicit annotation. At that snapshot, `getTrajectoryWindowWriter` has no caller; only its dead `createTrajectoryWindowWriter` path sets `activeOperation = "file-replace"`. No test changed in `7dd48eb`, and no existing test exercises `file-replace`. At upstream `4b85d834`, active trajectory persistence is SQLite and the queued writer never replaces files, so this type widening has no compatible upstream behavior to describe.

## Contracts not proven by any inventoried test

- End-to-end record-call order across two same-session recorders with reversed flush order.
- Correct behavior when one shared fork recorder flushes/closes while another retained recorder continues recording.
- Eviction followed by recreation of the same fork path, including append order, byte accounting, and awaited handle release.
- Configured `maxQueuedBytes` under the fork's default batched factory.
- A practical aggregate memory ceiling across fork writer paths, or any pending-memory ceiling for upstream SQLite recorders.
- A fork live-capture 10 MiB rolling window; source disproves it by selecting the 50 MiB file/export cap and append-stop semantics.
- Observable drop counts/reasons or default fork batched queue diagnostics.
- Actual append/open syscall counts despite the fork test names.
- Path replacement detection by the persistent handle; current tests permit continued writes to the unlinked old inode.
- ENOSPC, permission loss after open, append failure, close failure, SQLite busy/error, transaction rollback publication, or retry of a failed batch.
- Timer-based cleanup timeout preemption of synchronous SQLite work.
- Graceful signal flush, uncaught-exception flush, forced exit, `SIGKILL`, or power-loss durability in either snapshot.

## Static conclusion

The snapshots are not behaviorally compatible. Fork `47c4aff1` is not a drop-in strengthening of upstream's writer: it changes all generic queued-writer callers, removes configured queue backpressure from the default path, introduces persistent handles without universal close ownership, weakens actual diagnostics/error visibility, and replaces the then-current rolling trajectory window with a 50 MiB append-stop path while leaving contradictory tests and docs. `7dd48eb` only aligns a type with an unreachable old trajectory writer and supplies no runtime capability. Upstream `4b85d834` has explicitly weaker pre-flush memory and crash-loss guarantees, but its SQLite transaction, rolling persisted-byte limit, same-session sequence ownership, and error propagation are materially stronger after flush.

Proposal verdict: Reject porting or retaining `47c4aff1` and `7dd48eb` as a compatibility layer on `4b85d834`; they do not preserve the current trajectory storage contract and their narrower crash window does not offset the disproven queue, retention, ownership, diagnostics, and failure guarantees.
Confidence: High for the incompatibility and source-level contract findings; medium-high for the unexecuted OpenClaw tests and pinned fs-safe behavior because execution and external dependency source inspection were explicitly out of scope.
Evidence: Named commit blobs and local history, complete relevant OpenClaw writer/trajectory/cleanup source traces, and the static test inventory above; no runtime claims are inferred from test names alone.
