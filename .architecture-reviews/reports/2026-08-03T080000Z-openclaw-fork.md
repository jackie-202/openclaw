## Verified findings

### 1. Pipeline run evidence is an unbounded second history inside product Git

**Problem.** The repository stores product source and an external task system's mutable execution history under the same lifecycle. Plans, task descriptions, checkpoints, acceptance manifests/results, evidence, and generated learnings are preserved as repository content although their authority is the external task/KM pipeline. This creates two histories for one run: canonical pipeline state and a partial checkout projection.

**Evidence.**

- Git already tracks **247** files under `plans/` and **159** under `learnings/`; the current worktree adds **77** untracked plan files and **43** untracked learning files.
- `plans/checkpoints/` contains **217** files, including **121** acceptance-run files. Representative files record step completion, task IDs, session IDs, dispatch timestamps, evidence repair, and mutable resume state—not stable product design.
- No source, script, or documentation consumer was found for `plans/checkpoints`, `plans/tasks`, or `learnings/`. The npm package allowlist also excludes these roots.
- **29 of 202** present learning files have fewer than 100 non-heading characters. A representative generated learning has empty “What happened” and “What to do” sections, so preservation itself is being treated as value.
- Commit `2a4a68ea339` (“preserve local fork task artifacts before upstream sync”) mixed dozens of learnings/plans/checkpoints with source and dependency changes. Git history therefore preserves operational projection batches alongside product evolution.

**Impact.** Repository status becomes noisy enough to hide product changes; upstream sync and review must reason about two unrelated histories; stale checkpoints can contradict live task state; generated low-information records enlarge the apparent knowledge surface without improving decisions. There is no retention or completion transition, so every task adds permanent lifecycle state.

**Recommendation.** Make the external task/KM store the sole authority for plans, checkpoints, acceptance-run evidence, and raw generated learnings. Keep only deliberately curated architecture/design documents in product Git, with a human-readable stable path and explicit selection criterion. Ignore pipeline projection roots in this checkout after choosing a migration/retention policy for existing history. If reproducible evidence must accompany a product change, publish one immutable final summary linked by task ID—not the task state machine.

### 2. Repository-local trajectory pointers are incomplete runtime residue

**Problem.** Session trajectory state is materialized under the source checkout as pointer files, but the data they point to is absent. This is neither a usable runtime store nor product content.

**Evidence.**

- `.openclaw/agents/main/sessions/` contains **31** `*.trajectory-path.json` files: **29 untracked** and **2 tracked**.
- Every pointer names a repository-relative `*.trajectory.jsonl` runtime file; **0 of 31 targets exist**, and there are zero trajectory JSONL files in that directory.
- Neither pointer nor target pattern is ignored. Two pointers have already crossed into Git history, demonstrating that accidental versioning is not hypothetical.
- Package distribution excludes `.openclaw/`, and no product consumer requires committed pointer files.

**Impact.** The checkout advertises session state that cannot be resolved, creates recurring untracked noise, and risks publishing session identifiers. It also splits trajectory ownership between the real runtime location and dead pointers in source control.

**Recommendation.** Store both trajectory data and any locator metadata under the canonical OpenClaw runtime state directory, outside the repository. If a pointer is genuinely needed, derive it at runtime and keep it co-located with the session store. Add the repository-local runtime root/pattern to the ignore boundary and remove already tracked pointers only after confirming no migration consumer depends on them.

## Suspicions

None published. Temporary `.tmp-km-*.ts` files and the changelog baseline backup look like the same artifact-boundary failure, but this run did not establish their producer/retention contract strongly enough to make a separate recommendation. The backup also overlaps a prior review theme.

## Rejected hypotheses

- **All plans/learnings should simply be deleted.** Rejected as too broad: a curated design decision can legitimately belong with source. The finding concerns raw pipeline state and generated projections without a retention boundary, not the existence of repository documentation.
- **Acceptance evidence must remain in Git for reproducibility.** Current artifacts are mutable run bookkeeping with external IDs and incomplete evidence, not a self-contained immutable reproduction bundle. A single finalized summary can preserve traceability without importing the lifecycle.
- **Trajectory pointers are required package metadata.** Rejected: the package allowlist excludes `.openclaw/`, all current targets are absent, and no repository consumer was found.

## Self-critique

Moving artifacts out of Git could merely hide complexity if the external store lacks retention, querying, backup, or stable links. The recommendation therefore does not call for immediate deletion: first name the canonical store and retention policy, then migrate or archive once, and keep a thin immutable link from product history where auditability matters. Separating runtime evidence lowers coupling and sync blast radius; it does not combine security boundaries or centralize unrelated product decisions. Curated product architecture notes remain legitimate and should not be swept into an opaque database.
