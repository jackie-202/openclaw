## Verified finding

### 1. The bounded `sources` compatibility branch is already a second configuration authority whose removal condition is satisfied by one pending migration

**Problem**

The active Deliberation change introduces canonical per-source `pipelines`, but simultaneously accepts the old `sources` plus optional global `deliveryTarget`. This creates two external configuration languages for one runtime truth.

**Evidence**

- `src/config.ts` defines both `canonicalConfigSchema` and `legacyConfigSchema`, rejects mixed forms, generates legacy pipeline IDs, normalizes legacy targets, and only then exposes one `pipelines` runtime representation.
- `openclaw.plugin.json` independently publishes both forms through `oneOf`, duplicating the compatibility surface at manifest validation and runtime parsing boundaries.
- `src/config.test.ts` contains dedicated equivalence, rejection, and legacy Slack-shape coverage.
- The live `~/.openclaw/openclaw.json` entry still uses `sources`, so this is not dead code and cannot safely be removed first.
- The updated README explicitly says this branch is temporary and must be removed after live config and operational fixtures contain no legacy examples. This is a declared cutover, not a long-lived compatibility promise.
- The entire dual-form mechanism is in the current dirty Deliberation migration rather than established committed architecture, making this the cheapest point to close it.

**Impact**

Until removed, every configuration change has two validation authorities and two shapes to reason about. The extra branch adds generated identity rules, target field translation (`provider/channelId` versus `channel/target`), manifest alternatives, tests, and a future risk that schema and parser drift. Runtime is already canonical, so this complexity buys only migration time.

**Recommendation**

Treat compatibility as a two-step cutover in the same delivery sequence:

1. migrate the live Deliberation config and remaining operational fixtures to `pipelines`, and verify startup/intake with the canonical form;
2. immediately remove `legacyConfigSchema`, `legacyDeliveryTargetSchema`, `legacyPipelineId`, `normalizeLegacyTarget`, the manifest `legacyConfig` branch, legacy README text, and compatibility-only tests.

Do **not** remove the branch before step 1: the verified live configuration depends on it. Do not introduce a deprecation flag or deadline mechanism; that would add another lifecycle state to solve a one-time local migration.

## Suspicions

### Unconsumed `history-read-v1.json` and `history-read-v2.json` snapshots

Neither JSON file is loaded by runtime nor referenced by contract tests; implementation and tests independently encode both versions. They may be stale duplicate documentation. Concrete harm was not established, and external KM consumers may use them out of repository, so this is not promoted to a finding. Before deletion, verify the KM-side consumer and provenance workflow.

## Rejected hypotheses

### History-read v1 and v2 are redundant fallback protocols

Rejected. They have materially different request/response and range semantics: v1 returns bounded messages preceding `before`; v2 returns freshness after a cutoff with watermark and completeness evidence. Both branches are implemented and tested, including orchestration coverage. Removing v1 requires consumer/cutover evidence not present here.

### KM contract mirrors are competing runtime authorities

Rejected. `km-wire-v1.json`, `openclaw-overlay-v1.json`, `provenance.json`, and `cutover-controls-v1.json` serve as cross-repository acceptance fixtures. Contract tests verify hashes, adopted ownership, endpoint/control shape, and lifecycle equality. Runtime routing does not load these files. Their duplication is intentional boundary evidence rather than a second live decision-maker.

### Delivery lifecycle projections are unnecessary duplicated state

Rejected. Repetition of pipeline/target evidence across intake, reservation, invocation, and completion is used as immutable fencing and audit evidence around external provider side effects. Removing it would reduce local fields but weaken idempotency and outcome verification, shifting complexity into incident recovery.

## Self-critique

The main finding concerns active uncommitted work, so it is a simplification opportunity at a migration seam rather than proof of accumulated production debt. The compatibility code currently has legitimate value because live config still uses it. The recommendation is therefore conditional and ordered: migrate first, verify, then delete. Keeping both forms indefinitely would be needless complexity; deleting the old form now would be unsafe.

No recommendation collapses the OpenClaw/KM ownership boundary or removes delivery fencing. Those mechanisms look verbose, but they protect distinct authorities and irreversible external sends.
