## Verified findings

### 1. Two independent channel model authorities survive the legacy-removal commit

**Problem**

`channels.runtimeByChannel[*][*].model` and `channels.modelByChannel[*][*]` can both declare the model for one channel target. They are no longer fallback layers or a compatibility translation: they are deliberately separate resolvers with different consumers.

**Evidence**

- Normal/fresh reply execution, native slash fast path and harness dispatch use `resolveChannelRuntimeProfile()` and therefore `runtimeByChannel` (`src/auto-reply/reply/get-reply.ts`, `get-reply-native-slash-fast-path.ts`, `dispatch-from-config.ts`). Gateway session display also resolves this profile.
- `src/agents/agent-command.ts` still uses `resolveChannelModelOverride()` from `modelByChannel` for primary live model selection. `src/status/status-message.ts` uses it to attribute the selected model as a “channel override”.
- The old key remains a supported public surface across type/schema/help/label/validation/plugin SDK code and tests. It appears in 19 source files; `runtimeByChannel` appears in 26.
- `src/channels/model-overrides.test.ts` has an explicit test named “keeps runtime and legacy model resolvers separate”. For the same Discord target it asserts `runtimeByChannel` → `openai/gpt-5.5`, while `modelByChannel` → `openai/gpt-5.4`.
- Commit `435059f7d6` says “remove legacy channel model overrides”, but its diff exports the legacy resolver independently rather than removing the key. There is no migration/doctor path between the two keys.
- Sanitized current runtime evidence: `runtimeByChannel` exists for Discord with 11 entries; `modelByChannel` is absent. The local deployment has therefore already migrated away from the legacy authority.

**Impact**

A configuration containing both keys can select one model for message dispatch/native slash and another for agent-command selection or status attribution. Even when only one key is configured, maintainers must understand two schemas, two resolver contracts, repeated meta-key allowlists, two test families and path-dependent precedence. The advertised removal is incomplete, so the code communicates a simpler architecture than it actually has.

**Recommendation**

Make `runtimeByChannel` the fork's sole channel-scoped model authority:

1. First verify whether any supported external/fork deployment still contains `modelByChannel`; locally it does not.
2. If compatibility is required, implement one bounded config migration or a doctor diagnostic—not permanent dual runtime resolution.
3. Change agent-command selection and status attribution to the runtime-profile resolver.
4. Remove the legacy resolver, SDK exports, schema/type/help/label/validation branches and dedicated legacy tests once migration is complete.
5. Keep one shared target-matching implementation beneath the profile resolver; do not duplicate candidate matching while deleting the public legacy authority.

This is deletion of a competing authority, not movement of its complexity to another layer.

## Self-critique

- `modelByChannel` is upstream-originated, while `runtimeByChannel` is fork-specific. Keeping both can be defensible for upstream compatibility. The recommendation is therefore fork-scoped and migration-gated, not a claim that upstream must remove its key.
- A composite profile contains more than a model, so `runtimeByChannel` is not merely a rename. That boundary is legitimate; the problem is only that its `model` field duplicates another live model authority.
- A sudden schema deletion could break dormant configs or plugins. A one-time migration/diagnostic contains that blast radius better than indefinite fallback, but deployment inventory must precede removal.
- Status attribution may be diagnostic rather than execution authority. Even so, reporting against a different config source can misdescribe why the active model was selected, so it belongs on the same authority.
- Focused tests validate today's split rather than proving removal safe. The focused gate passed (4 files, 127 tests), confirming current behavior is intentional and stable; removal still needs migration tests and all execution-path precedence tests before implementation.

## Correction: Option A provenance review (2026-07-25)

This section corrects the recommendation in finding 1. It does not alter the original report above.

The recommendation to make `channels.runtimeByChannel` the canonical channel-model authority is withdrawn. The follow-up provenance review established that `channels.modelByChannel` is an upstream-owned public configuration and resolver surface, while model-bearing `runtimeByChannel` is fork-owned. Removing `modelByChannel` would therefore deepen the permanent fork delta rather than simplify it.

The approved correction is [proposal `proposal-20260724-083714-6c9e68`, Option A](../../docs/proposals/proposal-20260724-083714-6c9e68_minimize-channel-runtime-divergence-from-upstream.md): retain `channels.modelByChannel` as the sole persistent model authority, keep `runtimeByChannel` only as a model-free non-model runtime supplement, and treat live session values as cache or snapshot state rather than configuration authority.

This correction closes the architectural recommendation from review run `2026-07-24T080000Z-openclaw-fork`. It is independent of the implementation acceptance result recorded in `2026-07-24-option-a-closure.md`; failed or missing rollout evidence does not restore the superseded recommendation.
