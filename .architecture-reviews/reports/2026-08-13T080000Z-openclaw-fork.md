## Verified findings

### 1. iOS signing defaults have two competing authorities selected per target

**Problem**

The generated iOS project does not have one signing-default authority with explicit, narrow overrides. It has two independently maintained tracked base files:

- `apps/ios/Signing.xcconfig`
- `apps/ios/Config/Signing.xcconfig`

`apps/ios/project.yml` chooses the first for the app, share extension, activity widget, and tests, but the second for the watch app and watch extension. Both files claim to provide shared/default signing configuration and both include the same local override files.

**Evidence**

- `project.yml` lines 45–47, 169–171, 208–210, 307–309 and 340–342 select `Signing.xcconfig`.
- Lines 245–247 and 280–282 select `Config/Signing.xcconfig`.
- The root file defaults `OPENCLAW_CODE_SIGN_STYLE = Manual`, supplies app/share provisioning profiles, and includes `Config/Version.xcconfig`.
- The nested file defaults signing to `Automatic`, introduces a second team-selection variable chain, clears watch profiles, and includes `Version.xcconfig` from its own directory.
- Their variable contracts have already drifted: root signing declares share bundle/profile values that nested signing omits; nested signing declares watch profile values and direct Xcode signing assignments that root signing omits.
- Git history shows both continue to be changed together for cross-target features (for example commit `e60c5105607`, debug product identity), requiring duplicated edits rather than encoding the target distinction as an override.

**Impact**

A contributor changing team selection, local override behavior, debug bundle derivation, signing style, or provisioning semantics must understand which target belongs to which base file and keep two similar contracts synchronized. Missing one file can produce target-specific signing behavior rather than a clear config/check failure. The split also hides the legitimate distinction—release provisioning versus watch defaults—inside two broad authorities.

**Recommendation**

Create one canonical signing base containing shared version include, team selection, bundle identifiers, debug derivations, and local override order. Express genuine product/configuration differences as narrowly named overlays (for example a release provisioning overlay or explicit per-target settings in `project.yml`), not a second general-purpose signing base. Add a generation/check assertion that every target consumes the canonical base and only declared overlays. Preserve separate app/watch identifiers and provisioning requirements; remove only duplicated ownership.

## Self-critique

The app/watch boundary is legitimate: identifiers, profiles, and platform behavior differ. The recommendation therefore does **not** flatten target semantics or force all targets to use identical signing values. It centralizes only shared defaults and makes differences explicit overlays. This slightly increases coupling to a common base, but that coupling already exists implicitly through duplicated variables and synchronized commits; making it explicit reduces drift and blast radius. Before implementation, an iOS build matrix should prove that App Store/manual provisioning and local automatic watch signing still work.
